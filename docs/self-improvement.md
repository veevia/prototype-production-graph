# Self-improvement

> **TL;DR:** Every run ends by proposing what it learned. Lessons become candidate rules. A rule gets tested, is
> approved by a named human, is adopted into a rubric, and is then monitored across runs. Learning can never change
> product truth, requirements, evidence or approved design principles, and nothing unreviewed can block a run.

## Where knowledge lives

| Store | Scope | Changes through |
|---|---|---|
| `knowledge/rules.json` (74 generic defaults) | starter baseline | reviewed distribution changes only |
| `<private-project>/knowledge/rules.json` | one private project | explicit memory actions with `--rules`, versioned locally |
| `knowledge/public/evidence.json` | the evidence records behind the rules | rule updates |
| `knowledge/design-principles.md` | human-readable principles | generated from the rules (`pdg docs`) |
| `<project>/controls/memory.md` | one project | N19; its Lessons log is append-only |

## From feedback to a testable rule

The public profile recommends checks such as these; private feedback and source records are not distributed, and distribution defaults do not approve your project's decisions:

| Rule | Statement | Check |
|---|---|---|
| R-SCP-001 | Change only what the request or the defect scopes: refine, don't redesign, and re-open only the nodes a defect traces to | tool `regen:check_targeted` + test |
| R-IA-001 | When sources serve different business units, unify the shell and the components, not their domain workflows | reviewer dimension `DES-DOMAIN` |
| R-VIS-001 | Optimise for component consistency: one type scale (≤ 8 sizes), one radius set (≤ 5), one focus ring | tool `design_system:check` + reviewer |

Every rule has a statement, evidence references describing generic checks, a check (tool function, rubric dimension
or test), a threshold, a category, a scope (`stable` or `project_specific`) and an evidence class.

## The learning loop (N19)

1. **Lessons.** The learning agent writes lessons from the run's defects, comparisons, feedback and ledger. Each lesson
   has a scope (reusable or project-specific), an evidence class (verified · inferred · recommendation · missing) and
   evidence. `LRN-HONEST` refuses a `verified` lesson whose only support is simulated.
2. **Proposal.** The `learning` hook turns lessons into a proposal: observations on existing rules (did the rule fire,
   did it help?) and new candidates `R-NEW-<run>-L<n>`. The proposal is an artifact; nothing is applied.
3. **Apply.** A named human applies it: `pdg memory apply --proposal <file> --approved-by <human> --rules <private-project>/knowledge/rules.json`. Observations are
   recorded and candidates are added as `candidate`. A proposal is refused, with nothing written, if any item targets a
   protected scope or the applier is not a named human.
4. **Promote.** Each step up is a separate, gated command:

| Transition | Gate |
|---|---|
| candidate → validated | an executable check exists, the rule has evidence, and validation evidence is given (a test id or a run) |
| validated → approved | a named human (`--by Approver --human`); marks the rule confirmed |
| approved → adopted | `--adopted-in` names the rubric or config it lives in |
| adopted → monitored | at least one observation from a run after adoption |
| any → revised · retired | a reason and evidence; a named human for approved, adopted or monitored rules; a revision keeps the previous statement |

Transitions cannot skip a step. Every accepted change bumps the version, snapshots the previous file and appends to
the changelog; a refused change writes nothing.

## Honest seeding

The initial rule seed ([`knowledge/public/evidence.json`](../knowledge/public/evidence.json)) claims no automatic
human decision:

- An enforced generic distribution check is seeded `adopted`. Its initial entry reads
  `by: distribution, human: false` with basis `distribution-default`. It carries
  `confirmed_by_human: false` until `pdg memory confirm <rule> --by Approver` appends a real human approval.
  [`knowledge/seed-rule-review.md`](../knowledge/seed-rule-review.md) (regenerated by `pdg docs`) lists any still
  awaiting confirmation. `pdg memory confirm --all-seed --by Approver` confirms them all as one decision.
- Advisory generic checks are `validated`, and never blocking.
- Informational generic checks stay `candidate`. No project-specific decisions are bundled.

The 63 enforced defaults carry no human confirmation; 9 checks are advisory (`validated`) and 2 are informational
(`candidate`). A real confirmation is recorded only by an authorized human action on a private rule profile.

## What learning can never do

`protected_scopes` in the rule base: `product_truth`, `requirements`, `evidence`, `approved_design_principles`. A
lesson that would rewrite them is refused at N19 (`LRN-PROTECTED`) and again at `memory apply`. The run's own control
documents change only through their writers and change requests, never through learning.
